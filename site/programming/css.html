Question 1单选CSS · Code review

Requirement: centre .card both horizontally and vertically inside its parent .wrap. Which implementation is correct?

需求：让 .card 在其父容器 .wrap 内既水平居中、又垂直居中。下列实现正确的是：

要件：.card を親要素 .wrap の中で水平・垂直ともに中央に配置したい。正しい実装はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 C

On a flex container, justify-content aligns along the main axis (horizontal by default) and align-items along the cross axis (vertical by default); both are needed for two-axis centring. margin:auto only centres vertically when the parent is a flex or grid container — with a plain block parent it does nothing vertically. text-align affects inline content only, and vertical-align has no effect on block-level children. justify-content and align-items are container properties; written on the child they do nothing.

flex 容器上 justify-content 管主轴（默认横向）、align-items 管交叉轴（默认纵向），两个都给才能两轴居中。margin:auto 只在父级是 flex/grid 容器时才会垂直居中，父容器是普通块级时垂直方向完全不动。text-align 只影响行内内容，vertical-align 对块级子元素无效。justify-content 与 align-items 是容器属性，写在子项上不产生任何效果。

flex コンテナでは justify-content が主軸（既定は横）、align-items が交差軸（既定は縦）を揃える。両軸で中央に置くには両方が必要。margin:auto が縦に効くのは親が flex/grid コンテナのときだけで、通常のブロック親では縦方向には何も起きない。text-align はインライン内容にしか効かず、vertical-align はブロックレベルの子要素には無効。justify-content と align-items はコンテナのプロパティで、子要素に書いても効果はない。

Question 2单选CSS · Code review

Requirement: three .col children should split the row into exactly equal widths, regardless of how long their text is. Which implementation is correct?

需求：三个 .col 在容器内等宽平分，且不受各自文字长度影响。下列实现正确的是：

要件：3 つの .col を、それぞれの文字量に関係なく完全に等幅で分割したい。正しい実装はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 B

flex:1 expands to flex-grow:1; flex-shrink:1; flex-basis:0%. The key part is flex-basis:0% — every child starts from zero width and then receives an equal share of the free space, so text length cannot change the result. flex-grow:1 alone leaves flex-basis at auto, so the browser first allocates each child its content width and only splits what is left; columns drift apart as text lengths differ. width:33.33% ignores gaps and padding, and justify-content:space-between distributes spacing, not width.

flex:1 展开为 flex-grow:1; flex-shrink:1; flex-basis:0%。关键在 flex-basis:0% —— 先把所有子项基础宽度归零，再按比例平分剩余空间，所以文字长短不影响结果。只写 flex-grow:1 时 flex-basis 仍是 auto，浏览器会先按内容宽度分配、再分剩余空间，三列会随文字长度漂移。width:33.33% 没算间距和 padding；justify-content:space-between 分配的是间距而不是宽度。

flex:1 は flex-grow:1; flex-shrink:1; flex-basis:0% に展開される。要点は flex-basis:0%。すべての子の基準幅を 0 にしてから余白を等分するため、文字量に影響されない。flex-grow:1 だけだと flex-basis は auto のままなので、ブラウザーはまず内容幅を割り当て、残りを分ける。文字量が違えば列幅もずれる。width:33.33% は余白や padding を考慮せず、justify-content:space-between が配分するのは間隔であって幅ではない。

Requirement: a single line of text that is too long should end with an ellipsis (…). Which implementation is correct?

需求：单行文字超出容器宽度时显示省略号（…）。下列实现正确的是：

要件：1 行のテキストが幅を超えたときに省略記号（…）を表示したい。正しい実装はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 D

These three declarations work as a set and all are required. white-space:nowrap forces the text onto one line so that it can actually overflow; overflow:hidden performs the clipping; text-overflow:ellipsis only draws the ellipsis once clipping has already happened. Drop overflow:hidden and the text simply spills out of the box with no ellipsis. Drop white-space:nowrap and the text wraps normally, so there is no overflow and no ellipsis either. When reviewing, seeing text-overflow should send you looking two lines up to confirm the other two.

这三个属性是绑定套装，缺一不可。white-space:nowrap 强制不换行，制造「一行放不下」的前提；overflow:hidden 真正把超出部分裁掉；text-overflow:ellipsis 只在已经发生裁剪时才画省略号。少了 overflow:hidden，文字直接溢出容器，省略号不出现；少了 white-space:nowrap，文字正常折行，压根不产生溢出。审查要点：看到 text-overflow 就往上翻两行，确认另外两个在不在。

この 3 つはセットで、すべて必要。white-space:nowrap が 1 行に固定して「入りきらない」状態を作り、overflow:hidden がはみ出しを切り、text-overflow:ellipsis は切り取られたときにだけ省略記号を描く。overflow:hidden がなければ文字はそのままあふれ、省略記号は出ない。white-space:nowrap がなければ普通に折り返すので、あふれ自体が起きず省略記号も出ない。レビューでは text-overflow を見たら 2 行上を確認する。

Question 4单选CSS · Code review

Requirement: an image should scale down proportionally without distortion and never exceed its container width. Which implementation is correct?

需求：让图片在容器内等比缩放、不变形，且不超过容器宽度。下列实现正确的是：

要件：画像を縦横比を保ったまま縮小し、コンテナ幅を超えないようにしたい。正しい実装はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 A

max-width:100% caps the width without ever enlarging, and height:auto keeps the ratio — this is the only combination that neither distorts nor overflows nor upscales. width:100% forces the image to fill the container unconditionally, so a 200px image is stretched and blurred. object-fit controls how an image fills its own box; it does not constrain the box, so an already-oversized image still overflows. height:100% falls back to auto when the parent has no fixed height, and even when it applies it stretches the image and breaks the aspect ratio.

max-width:100% 只压上限、不放大，height:auto 让高度按比例走 —— 只有这个组合同时满足「不变形 + 不溢出 + 不放大」。width:100% 是无条件拉伸，200px 的小图会被拉满容器变模糊。object-fit 管的是图片在自身盒子内怎么填充，不约束盒子尺寸，图片本身超宽时照样溢出。height:100% 在父容器没有固定高度时会被解析成 auto；就算生效也是强制拉伸，长宽比直接崩。

max-width:100% は上限だけを抑えて拡大はせず、height:auto が比率を保つ。変形・はみ出し・拡大のどれも起きないのはこの組み合わせだけ。width:100% は無条件に引き伸ばすので、200px の画像はぼやける。object-fit は画像が自分のボックス内をどう埋めるかの指定で、ボックス自体は拘束しないため、もともと大きい画像はやはりはみ出す。height:100% は親に高さがなければ auto になり、効いても縦横比が崩れる。

Question 5单选CSS · Code review

Requirement: an element must be invisible, must not respond to mouse clicks, and must still keep the space it occupies in the layout. Which declaration does that?

需求：让一个元素不可见、不响应鼠标点击，但仍保留它占据的布局空间。应该用：

要件：要素を見えなくし、クリックにも反応させず、ただしレイアウト上の占有スペースは残したい。どれを使うか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 C

visibility:hidden keeps the box in the layout, blocks pointer events and is skipped by screen readers. opacity:0 is the trap here — the element stays in the layout and still receives clicks, so an invisible layer above a button produces a puzzling 'the button does not work' bug. display:none removes the element from the layout entirely and surrounding content jumps. Pushing it off-screen with position:absolute creates a phantom scroll area and should not appear in new code.

visibility:hidden 保留占位、不响应点击、屏幕阅读器跳过。opacity:0 是最隐蔽的坑 —— 元素照样占位、照样接收点击，如果它盖在按钮上方，用户会遇到「点不动」的诡异问题。display:none 会让元素彻底移出布局，周围内容会跳位。用 position:absolute 把它推到屏幕外的老式写法会凭空撑出滚动区域，新代码里不该再出现。

visibility:hidden はレイアウト上の場所を保ち、ポインター操作を受け付けず、スクリーンリーダーも読み飛ばす。落とし穴は opacity:0。場所は保たれ、クリックも受け付けるため、ボタンの上に重なっていると「ボタンが押せない」という不可解な不具合になる。display:none はレイアウトから完全に外れ、周囲がずれる。position:absolute で画面外へ飛ばす旧式の手法は不要なスクロール領域を生む。

Question 6单选CSS · Code review

Requirement: add a 0.2-second transition. From a performance standpoint, which declaration is the best choice?

需求：给元素加一个 0.2 秒的过渡动画。从性能角度看，下列写法最合理的是：

要件：0.2 秒のトランジションを付けたい。パフォーマンスの観点で最も適切な指定はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 A

transition:all is the one to stop in review: it watches every animatable property, so any unexpected change (a stray padding tweak from JavaScript, for instance) starts animating, and the browser does far more interpolation work. opacity and transform are compositor properties — their transitions can run entirely on the GPU without triggering layout or paint. width, height, top and left all trigger layout recalculation on every frame, which is the most expensive option. transition: 0.2s is simply invalid syntax: a property and a duration are both required.

transition:all 是 review 里见到就该拦下的写法：它会监听每一个可动画属性，元素上任何意料之外的样式变化都会触发过渡，浏览器的插值计算量成倍上升。opacity 与 transform 是合成属性，过渡可以完全交给 GPU，不触发重排和重绘。width / height / top / left 全部会触发重排，每帧都要重新计算布局，是最贵的写法。transition: 0.2s 是语法错误：属性和时长都必须给。

transition:all はレビューで止めるべき書き方。すべてのアニメーション可能なプロパティを監視するため、想定外の変更（JavaScript による padding の微修正など）でもアニメーションが走り、補間の計算量が跳ね上がる。opacity と transform はコンポジターのプロパティで、GPU だけで処理でき、レイアウトも描画も発生しない。width / height / top / left は毎フレーム再レイアウトを起こす最も高コストな指定。transition: 0.2s はプロパティと時間の両方が必要なため文法エラー。

Question 7单选CSS · Code review

Requirement: font sizes must scale with the root font size the user sets in the browser (an accessibility requirement). Which unit should be used?

需求：字号要能跟随用户在浏览器里设置的根字号统一缩放（无障碍要求）。应该用哪个单位？

要件：ブラウザーでユーザーが設定したルートフォントサイズに合わせて文字を拡縮したい（アクセシビリティ要件）。どの単位を使うべきか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 D

rem is always relative to the root element's font size, giving one site-wide baseline, and it respects the default size the user has configured in the browser. em and percentages are both relative to the parent's font size and therefore compound: nested lists with font-size:0.9em three levels deep end up at roughly 0.9³ ≈ 0.73 times. vw follows the viewport width, not the user's font setting, and on very wide screens it grows out of control unless clamped.

rem 始终相对根元素字号，全站一个基准，并且尊重用户在浏览器里调整的默认字号 —— 这是无障碍场景的标配。em 和百分比都相对父元素字号，会层层累积：嵌套列表里写三层 font-size:0.9em，文字会缩到 0.9³ ≈ 0.73 倍。vw 跟随视口宽度，与用户设置的字号无关，而且在超宽屏上会大到失控（通常要配 clamp() 夹住）。

rem は常にルート要素のフォントサイズを基準にするため、サイト全体で基準が 1 つになり、ユーザーがブラウザーで設定した既定サイズも尊重される。em と % は親のフォントサイズ基準で累積するため、リストを 3 段ネストして font-size:0.9em と書くと約 0.9³ ≈ 0.73 倍まで縮む。vw はビューポート幅に従い、ユーザーの文字サイズ設定とは無関係。広い画面では clamp() で上下限を付けないと大きくなりすぎる。

Question 8单选CSS · Code review

Which of these CSS properties is NOT inherited by child elements?

下列 CSS 属性中，不会被子元素继承的是：

次の CSS プロパティのうち、子要素に継承されないものはどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 B

Box-model properties — width, height, margin, padding and border — are never inherited. That is deliberate: if they were, setting one width on a parent would lock every descendant to the same width. Inheritance covers mostly typographic properties: font-size, color, line-height, font-family, letter-spacing and text-align. A related review note: a rule such as * { font-size: 14px } added to 'unify font sizes' is redundant, because fonts already inherit; only the non-inherited properties need to be set explicitly.

盒模型类属性 —— width、height、margin、padding、border —— 都不继承。这是 CSS 的刻意设计：否则给父元素设一个宽度，所有后代都会被同一个宽度锁死。会继承的主要是文字相关属性：font-size、color、line-height、font-family、letter-spacing、text-align。一条相关的审查意见：为了「统一字号」写 * { font-size: 14px } 是多余的，字号本来就继承；真正需要显式设置的是那些不继承的属性。

ボックスモデル系のプロパティ（width、height、margin、padding、border）は継承されない。これは意図的な設計で、もし継承されると親の幅がすべての子孫を縛ってしまう。継承されるのは主に文字関連（font-size、color、line-height、font-family、letter-spacing、text-align）。関連するレビュー指摘として、「文字サイズを統一する」ために * { font-size: 14px } と書くのは冗長。文字サイズはもともと継承されるので、明示が必要なのは継承されないプロパティだけ。

Question 9单选CSS · Code review

Requirement: define a brand-colour variable and fall back to a safe value when that variable is undefined. Which declaration is correct?

需求：定义一个品牌色变量，并在该变量未定义时回退到一个安全值。正确写法是：

要件：ブランドカラーの変数を定義し、未定義のときは安全な値にフォールバックさせたい。正しい書き方はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 C

var() takes the fallback as its second argument, separated by a comma; the fallback is used when the variable is undefined or its value is invalid. This is very handy in component libraries: the component ships a default colour and consumers can override --brand or not. var(--brand) #333 is two adjacent values, so the whole declaration is discarded. CSS has no || operator — that is JavaScript syntax. A fallback must be a concrete value, not another variable name: var(--brand, --safe) would literally try to use the string --safe as a colour. Chained fallbacks need var(--brand, var(--safe, #333)).

var() 的第二个参数是回退值，用逗号分隔：变量未定义或值无效时取它。这在组件库里很实用 —— 组件自带一套兜底色，接入方可以选择性覆盖 --brand。var(--brand) #333 是两个并排的值，整条声明会被丢弃。CSS 里没有 || 运算符，那是 JS 写法。回退值必须是具体值而不是另一个变量名，var(--brand, --safe) 会真的拿字符串 --safe 当颜色用；要链式兜底得写 var(--brand, var(--safe, #333))。

var() の第 2 引数がフォールバック値で、カンマで区切る。変数が未定義、または値が無効なときに使われる。コンポーネントライブラリーでは便利で、部品側が既定色を持ち、利用側が --brand を上書きするかどうかを選べる。var(--brand) #333 は値が 2 つ並ぶため宣言ごと破棄される。CSS に || 演算子はなく、それは JavaScript の書き方。フォールバックは具体的な値でなければならず、var(--brand, --safe) は文字列 --safe を色として解釈してしまう。連鎖させるなら var(--brand, var(--safe, #333))。

Question 10单选CSS · Code review

Requirement: build a two-column grid with equal column widths. Which declaration is correct?

需求：用 Grid 做一个两列等宽布局。下列写法正确的是：

要件：Grid で 2 列の等幅レイアウトを作りたい。正しい書き方はどれか。

  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 A

1fr means one share of the free space, so repeat(2, 1fr) gives two equal columns. The easiest mistake to miss is in the third option: repeat() requires a comma between its two arguments, and writing a space makes the whole grid-template-columns declaration invalid — silently, with no console error. The page just collapses to a single stacked column, which is easy to wave through in review. 1fr 1fr 1fr defines three columns rather than two, and in the grid shorthand the slash separates rows from columns, so grid: 2 / 1fr means two rows and one column — the opposite of the requirement.

1fr 表示一份剩余空间，repeat(2, 1fr) 即两列各占一半。最容易漏看的是第三项：repeat() 的两个参数之间必须是逗号，写成空格会导致整条 grid-template-columns 声明无效，而且不会报错 —— 页面只是悄悄退化成单列堆叠，很容易在 review 中被放行。1fr 1fr 1fr 定义的是三列。grid 简写里斜杠分隔的是行与列，grid: 2 / 1fr 的含义是「两行、一列」，跟需求正好相反。

1fr は余白 1 つ分を意味し、repeat(2, 1fr) で等幅 2 列になる。見落としやすいのは 3 番目で、repeat() の 2 引数の間にはカンマが必要。空白にすると grid-template-columns の宣言全体が無効になるが、エラーは出ない。ページは黙って 1 列に退化するだけで、レビューでは流されやすい。1fr 1fr 1fr は 3 列の定義。grid 省略記法のスラッシュは行と列の区切りなので、grid: 2 / 1fr は「2 行 1 列」となり要件と正反対。

Question 11单选CSS · Code review

Review this CSS. The design says the card's total width must be exactly 200px, but it measures 242px. What is wrong and how should it be fixed?

审查下面这段 CSS：设计稿要求卡片总宽正好 200px，但实测占了 242px。问题出在哪，该怎么改？

次の CSS をレビューする。設計ではカードの全幅をちょうど 200px にするはずが、実測は 242px だった。原因と正しい修正はどれか。

.card {
  width: 200px;
  padding: 20px;
  border: 1px solid #ccc;
}
  1. A
  2. B
  3. C
  4. D
解析 / Explanation

正确答案 B

With the default box-sizing: content-box, width constrains the content box only, and padding and border are added outside it: 200 + 20×2 + 1×2 = 242px, which matches the measurement exactly. Adding box-sizing: border-box makes width mean the border box, so padding and border eat into the content area and the total stays at 200px. Using max-width just caps the box while the content area shrinks to 158px, so the layout is still wrong. Removing the border or switching padding to a percentage works around the symptom instead of fixing the cause. A useful review habit: if the project has no global *, *::before, *::after { box-sizing: border-box } reset, treat every hand-written width as suspect.

默认 box-sizing: content-box 时，width 只约束内容区，padding 和 border 往外叠加：200 + 20×2 + 1×2 = 242px，正好对上实测值。加上 box-sizing: border-box 后，width 变成边框盒总宽，padding 和 border 向内挤压内容区，总宽锁定 200px。改成 max-width 只是把上限压住，内容区实际只剩 158px，布局仍然错位。去掉 border 或把 padding 换成百分比都是在绕开症状，不是解决原因。一条有用的审查习惯：如果项目里没有全局的 *, *::before, *::after { box-sizing: border-box } 重置，那么每一处手写的 width 都值得怀疑。

既定の box-sizing: content-box では width は内容領域だけを拘束し、padding と border は外側に加算される。200 + 20×2 + 1×2 = 242px で実測値と一致する。box-sizing: border-box を加えると width はボーダーボックス全体の幅になり、padding と border が内側に食い込んで合計は 200px に固定される。max-width に変えても上限を押さえるだけで内容領域は 158px になり、レイアウトは依然としてずれる。border を外したり padding を % にするのは症状を避けているだけで原因は解決しない。有用な習慣として、プロジェクトに *, *::before, *::after { box-sizing: border-box } の全体リセットがなければ、手書きの width はすべて疑ってよい。

The other options are wrong: :hover applies to any element, cursor only changes the pointer shape, and the background shorthand participates in the cascade normally.

优先级要逐位比较。 #submit 是 (0,1,0,0) —— 一个 ID；.btn:hover 是 (0,0,2,0) —— 一个类加一个伪类。ID 位压过类位，所以 #submit 无条件胜出，hover 的颜色永远不生效。首选修法是把基础样式也改成类选择器 .btn { ... }，把 ID 从样式表里彻底拿掉。把 hover 规则改成 #submit:hover 也能生效，但会继续积累 ID 债务；用 !important 同样能生效，却会让后续所有覆盖失效，是技术债的起点。审查信号：样式表里出现 ID 选择器本身就该被标记，因为它权重太高，会让后面所有基于类的覆盖都失效 —— 这也是 BEM、CSS Modules、Tailwind 都刻意避开 ID 的原因。其余选项都不对：:hover 对所有元素生效，cursor 只改鼠标指针形状，background 简写完全可以参与层叠。

詳細度は 4 つの位置を順に比較する。#submit は (0,1,0,0) で ID が 1 つ。.btn:hover は (0,0,2,0) でクラス 1 つと疑似クラス 1 つ。ID の位置がクラスの位置に勝つため、#submit が常に優先し、ホバー時の色は適用されない。最善の修正は基本側もクラスセレクターにして .btn { ... } とし、スタイルシートから ID を完全に排除すること。#submit:hover に変えても効くが ID の負債が積み上がる。!important も効くが、以降の上書きがすべて失敗するようになり技術的負債の始まりになる。レビューの合図として、スタイルシート内の ID セレクター自体が指摘対象になる。重みが高すぎて、後から書くクラスベースの上書きがすべて効かなくなるためだ。BEM、CSS Modules、Tailwind が ID を避けるのはこの理由による。他の選択肢は誤り：:hover はどの要素にも効き、cursor はポインターの形を変えるだけで、background の省略記法は通常どおりカスケードに参加する。
